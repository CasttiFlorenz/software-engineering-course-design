# 研改｜需求调研计划

围绕一个班的一次课程作业，访谈教师、助教或实际负责互评的人，以及有过交作业和评阅经历的学生。请受访者复盘真实案例，记录现有做法、遇到的问题和例外。

## 调研方法

课程要求进行**真人干系人访谈并保留纪要**。每位组员应参与真实访谈，并在报告中关联覆盖自己两个调研点的纪要。可以联合访谈同一位学生、教师或助教。问卷可以补充访谈，用于了解痛点是否普遍。有问卷时，保留题目、发放对象、有效回收数和脱敏结果摘要。

- **半结构化访谈（主要方法）**：请学生、教师或助教复盘最近一次真实作业。先问当时怎么做，再追问卡在哪里、怎么解决、遇到例外由谁处理。比如问「你最后怎么确认该交 PDF 还是源文件？」
- **流程走查**：请受访者演示一次找答复、查看互评任务或处理漏评的过程。记下入口、步骤、信息断点和替代做法。
- **问卷（按需）**：访谈发现反复出现的问题后，用简短问卷了解其普遍程度。记录回收数量和适用人群。
- **竞品对照（按需）**：用同一个任务对照 Canvas 等现有工具，记录操作步骤和观察结果。把产品观察与访谈发现分别注明。

## 组员提交要求

1. 每人按上表负责两个调研点，参与真人干系人访谈。可联合访谈，纪要可以共用。记录日期、匿名代号与角色、关键问答、现有流程和需求发现。
2. 每人交一份覆盖两点的 Markdown 报告和至少两条用户故事。报告放在 `docs/research-reports/`，附纪要或链接。故事放在 `docs/user-stories/`，每条聚焦一个用户目标，写清角色、目标和价值，并关联报告对应章节。一个调研点可以支持多条故事，例如 `R03-1.md` 与 `R03-2.md`。公开材料先脱敏。
3. 从最新 `main` 开个人分支，如 `docs/research-r03-r04`。只暂存自己负责的文件，提交、推送后向 `main` 开 PR。在 PR 中列调研编号、报告和故事路径，由一名组员核对证据与故事是否对应，批准后合并。

```sh
git switch main
git pull --ff-only
git switch -c docs/research-r03-r04
# 写好报告与故事后，只暂存本次提交涉及的文件
git add docs/research-reports/R03-R04-Research-Reports.md docs/user-stories/R03-1.md docs/user-stories/R03-2.md docs/user-stories/R04-1.md docs/user-stories/R04-2.md
git commit -m "docs(research): 补充 R03 和 R04 调研与用户故事"
git push -u origin docs/research-r03-r04
```

以上步骤完成后，完成以下要求：

1. **整理用例清单。** 根据课堂点评，从故事初稿补齐至少 20 个用例，其中至少 2 个覆盖非功能需求，例如匿名身份保护、私有评语讨论访问控制。按参与者和业务目标去重。任务已发布和未发布是同一「查看互评任务」用例的两个验收场景。
2. **编写用例和验收标准。** 为用例编号，写清名称、参与者、目标、前置条件、主流程、关键异常和结果。每条用户故事补齐 Given / When / Then，逐条建 GitHub Issue、分配负责人，关联调研依据和用例编号。
3. **完善用例图和 SRS 草稿。** 用例图标出系统边界及学生、教师、助教等参与者。需求分析师汇总功能需求、非功能需求与约束，在 SRS 草稿中引用用例清单，并初步记录需求与用例的映射。课前将草稿提交 PR，课堂准备讲解用例图、关键场景和非功能约束。

| 课前核对 | 文件位置与 GitHub 记录 |
| --- | --- |
| 用例清单与验收标准 | 用例清单放 `docs/requirements/`，故事保存在 `docs/user-stories/`，在对应 Issue 记录负责人和链接 |
| 用例图与关键场景描述 | 图源放 `docs/models/`，文字描述放 `docs/requirements/` |
